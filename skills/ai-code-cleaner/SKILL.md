# AI Code Cleaner

扫描代码中 AI 最容易犯的各类错误，生成报告，并安全地修复可修复的问题。

## 触发方式

本技能**仅手动触发**。当用户输入 `/ai-code-cleaner` 时运行，可附带路径或 glob 缩小扫描范围（如 `/ai-code-cleaner src/agents/`）。若未指定范围，则扫描整个仓库。

## 前置条件

本技能需要并行启动三个子智能体进行审查。如果当前环境不支持子智能体，**立即告知用户并终止**，建议用户切换到支持子智能体的环境。不要尝试回退到单智能体串行模式——实测证明那样会显著降低召回率，审查结果不值得信赖。

## 工作流程

### 阶段一 — 确定范围与报告位置

1. 确定扫描范围：用户参数优先；否则扫描整个仓库。
2. 查找仓库已有的文档目录（如 `docs/`、`.github/`、`doc/`），将报告放在 `<文档目录>/ai-code-issues.md`。若无文档目录则放在仓库根目录。
3. 若报告文件已存在，先读取其内容——追加而非覆盖。

### 阶段二 — 并行三维度审查

**同时**启动三个只读子智能体，各自负责不同的审查维度。三个维度的划分依据是"工作方式的注意力分配"——它们需要的阅读策略天然冲突，放在一个智能体里会互相挤占注意力：

#### 子智能体 A：逐文件审查员

加载 `file-by-file-reviewer.md`。工作方式是一个文件一个文件地细看，看完一个再看下一个。负责那些只看单个文件就能发现的问题。

#### 子智能体 B：跨文件比对员

加载 `cross-file-comparator.md`。工作方式是先用 grep 搜出模式，再交叉比对多个文件。负责那些需要全局视角才能发现的问题。

#### 子智能体 C：契约审查员

加载 `contract-reviewer.md`。工作方式是先读架构文档和类型定义建立"应该是什么样"的预期，再回头审查代码是否违反契约。负责那些需要理解设计意图才能判定的问题。

**给每个子智能体的指令必须包含：**
- 扫描范围
- 明确告知它：不要写报告、不要改代码，只输出候选发现列表
- 明确告知它：你只是三个审查员之一，如果在工作过程中**顺便**发现了不属于你负责类别的问题，也记录下来，不用为这类额外发现提供详细证据

### 阶段三 — 合并与去重

主协调器收到三路结果后：

1. **去重**：同一文件同一根因只保留一条，合并各方发现。
2. **核验**：对每条候选用 read / grep / LSP 快速确认，排除明显误报。
3. **分类**：为每个确认的问题分配修复层级（安全 / 权衡 / 延后）。

注意：核验的目的是排除误报，不是筛选"重要性"。只要问题是真实存在的，无论价值高低都保留。

### 阶段四 — 根因分析（可选，人类决定）

合并去重完成后，询问用户是否要对这些发现进行深层根因分析。根因分析会将症状追溯到产生它们的设计缺陷源头——那些让代码库处于"容易写错"状态的设计决策。

如果用户同意：

1. 启动第四个子智能体，加载 `root-cause-analyzer.md`。
2. 将合并后的全部候选发现列表（原文）作为输入传给它。
3. 该智能体用自上而下的方法（先读类型/接口声明建立预期，再向下追踪症状）识别根因。
4. 收到根因分析结果后，整合进最终报告（见报告格式）。

### 阶段五 — 报告与咨询

1. 将结果写入报告 Markdown 文件（见报告格式）。若执行了根因分析，报告以根因为主线组织；否则按类别分组。
2. 对**权衡**类问题，将所有需要决策的项汇总到一次 `AskUserQuestion`、`askQuestions` 或类似功能的工具调用中，让人类一次性作答。每项附上你的推荐。若根因分析揭示了某个权衡项的上游成因或未来诱导效应，将此信息一并呈现给人类以辅助决策。
3. 收到人类答复后，更新报告中对应的选择结果。

### 阶段六 — 修复（必须在人类批准后才允许执行）

执行已批准的修复。对任何权衡类修复，确保有验证手段——运行现有测试，若无覆盖则编写最小化测试。报告修复内容及测试执行情况。

## 报告格式

根据是否执行了根因分析，报告使用不同的组织结构。

### 无根因分析时：按类别分组

```markdown
# AI 代码问题

> 由 ai-code-cleaner 生成于 YYYY-MM-DD
> 扫描范围：<扫描路径或"整个仓库">

## 概览

- 共发现 X 个问题（Y 个安全修复、Z 个权衡修复、W 个延后处理）

## 安全修复

### [类别名称]

- **文件：** `path/to/file.cs:42` — 问题描述
  - **修复：** 具体做法

## 权衡修复

### [类别名称]

- **文件：** `path/to/file.cs:88` — 问题描述
  - **保守方案：** 描述
  - **激进方案：** 描述
  - **推荐：** 推荐哪个及理由
  - **选择：** _（人类决策后填写）_

## 延后处理

### [类别名称]

- **文件：** `path/to/file.cs:120` — 问题描述
  - **未来方向：** 后续优化建议
```

### 有根因分析时：根因在前，独立问题在后

```markdown
# AI 代码问题

> 由 ai-code-cleaner 生成于 YYYY-MM-DD
> 扫描范围：<扫描路径或"整个仓库">

## 概览

- 共发现 X 个问题，归因为 N 个根因 + M 个独立问题

## 根因

### 根因 1：<一句话概括设计缺陷>

- **根因模式：** <模式名>
- **设计缺陷描述：** 这个设计状态为什么会持续诱导错误代码
- **未来诱导效应：** 不修复时，未来代码会怎样继续犯错
- **修复方向：** 应该怎么改设计
- **影响面：** 安全 / 权衡 / 延后

**关联症状：**

- `path/to/file.cs:42` — 问题描述（安全）
  - **修复：** 根因修复后此处如何处理
- `path/to/file.cs:88` — 问题描述（权衡）
  - **保守方案：** 描述
  - **激进方案：** 描述
  - **推荐：** 推荐哪个及理由
  - **选择：** _（人类决策后填写）_

### 根因 2：...

## 独立问题

以下发现没有上游设计缺陷，问题本身即是终点。按修复层级分组：

### 安全修复

- **文件：** `path/to/file.cs:42` — 问题描述
  - **修复：** 具体做法

### 权衡修复

- **文件：** `path/to/file.cs:88` — 问题描述
  - **保守方案：** 描述
  - **激进方案：** 描述
  - **推荐：** 推荐哪个及理由
  - **选择：** _（人类决策后填写）_

### 延后处理

- **文件：** `path/to/file.cs:120` — 问题描述
  - **未来方向：** 后续优化建议
```

## 重要事项

- 未经人类批准，绝不自动修复权衡或延后类问题。
- 修复代码后始终运行现有测试以捕获回归。若无测试覆盖且修复非平凡，编写最小化测试。
- 以项目自身的约定（来自 AGENTS.md、CLAUDE.md、CONTRIBUTING.md、lint 配置）为权威来源。本技能的检查类别是补充性的。
- 若仓库已有 lint 规则覆盖了某项检查，标注为"已有规则覆盖"并跳过。
