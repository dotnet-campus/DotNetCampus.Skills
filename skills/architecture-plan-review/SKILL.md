# 架构遵循性代码计划审查

当 AI 编写完一个版本计划之后，本技能指导 AI 审查该计划的架构遵循性问题，并指导修复。

---

## 审查流程

### 第一步：收集信息

收集并汇总以下信息，确保充分理解全部需求：

1. **本次对话中人类提出的所有问题**（高优先级）——回顾对话，总结需求
2. **要审查的计划文档本身**（中高优先级）——读取计划文件全文
3. **架构设计要求**（中优先级）——定位并读取项目的架构信息源：
   - 项目根目录的 CLAUDE.md / AGENTS.md（通常包含架构概述和关键决策）
   - docs/ 目录下的架构设计文档
   - 其他包含架构约束、设计原则的文件

如果参数中未指定计划文档路径，自行在项目中搜索（常见位置：docs/ 目录、项目计划目录等）。

### 第二步：总结模块划分

根据收集到的架构信息，总结出清晰的模块划分表：

- 每个模块的名称、职责和边界
- 模块间的依赖关系和通信方式
- 明确的职责分离原则（哪些事情属于哪个模块，哪些事情不属于）

这一步的产物是后续所有审查的"架构基准"，所有子智能体都将以此为依据。

### 第三步：按模块边界重组计划文档

这一步是本技能最核心的产出——不只是审查问题，而是**改写计划文档的组织结构**，使其按架构模块边界分组。

**为什么这一步如此重要**：计划文档会被后续的代码编写阶段 AI 直接阅读并执行。如果计划按模块组织任务，AI 在实施时会天然感知到"我正在修改模块 A"→"这个改动是否越出了模块 A 的边界"。文档结构本身就成为了架构护栏——它不需要 AI 刻意遵守架构，而是让架构边界成为任务的自然分界线。反之，如果计划只按时间顺序或功能点罗列任务，AI 实施时会把所有任务视为一个扁平列表，容易忽视模块边界。

**具体做法**：

1. 将实施计划中的「阶段」改为按架构模块组织的章节。每个章节对应一个架构模块，章节标题明确标注模块名称。

2. 将每个任务归入其所属模块的章节：
   - 明确属于某模块的任务 → 直接归入该模块章节
   - 跨模块任务 → 归入核心所在模块的章节，在任务描述中用显眼标注说明"此任务涉及 {其他模块} 的同步修改：{具体内容}"
   - 完全跨越多个模块的全局性任务（如全量文本替换） → 放到独立的"全局任务"章节

3. 在每个模块章节的开头，用一两句话重申该模块的职责边界和关键约束（从第二步的模块划分表中提取），使后续 AI 在阅读该章节时立即建立边界意识。

4. 如果原计划有阶段划分（第一阶段、第二阶段……），在模块章节内部保留阶段标注（如任务前标注"[阶段1]"），但章节层级以模块为主、阶段为辅。

**注意**：不要只做检查就跳过——必须实际改写计划文档的结构。这一步的产物是一份按模块组织的计划文档，不是一份"模块归属检查报告"。

### 第四步：调用子智能体进行独立审查

同时启动多个子智能体（防止上下文污染）。每个子智能体都必须自行阅读架构源文件，不依赖主智能体的总结。

**1 号子智能体——需求完整性审查：**
- 重新阅读计划文档
- 对照人类提出的所有需求，确保无遗漏
- 检查全文描述清晰无歧义、无前后矛盾

**2 号子智能体——架构合规性审查：**
- 自行阅读架构源文件（CLAUDE.md、架构文档等）
- 阅读计划文档
- 检查每个任务是否符合架构原则

**3+ 号子智能体——需求可行性评估：**
- 自行阅读架构源文件（与 2 号相同的来源）
- 按架构边界划分探索范围，每个子智能体负责一个模块
- 在理解架构要求的前提下探索代码，评估可行性
- 区分"当前代码现状"与"架构要求"——以架构要求为准

### 第五步：汇总与修复

将所有子智能体的审查结果汇总后：

1. **在第三步产出的模块化文档结构上修改**：修复发现的缺陷、遗漏、重复、矛盾。新增的任务必须归入正确的模块章节，不能随意追加到文档末尾
2. **新增「需求可行性评估」章节**：将可行性评估结果写入计划文件的独立章节
3. **新增「单元测试原则」章节**（如不存在）：

```markdown
## 单元测试原则

- 如发现单元测试不通过，优先保证代码符合架构要求和设计原则，禁止为通过测试而破坏架构
- 如实在难以兼顾测试和架构要求，宁可忽略单元测试，也不能破坏架构
- 如存在因此而忽略的单元测试，执行结束后必须告知人类（优先记录到总结文档）
```

## 子智能体 Prompt 模板

### 1 号：需求完整性审查

```
你是需求完整性审查员。请阅读以下计划文档，对照人类需求列表，检查：
1. 人类需求是否全部被覆盖
2. 文档描述是否清晰无歧义
3. 是否存在前后矛盾

人类需求列表：
{需求列表}

计划文档路径：{路径}

输出格式：列出所有问题，每个问题注明位置和建议修改。无问题则明确说明"未发现问题"。
```

### 2 号：架构合规性审查

```
你是架构合规性审查员。

第一步：阅读以下架构源文件，理解项目的架构要求和设计原则：
{架构文件路径列表}

第二步：阅读计划文档，逐个检查任务是否符合架构原则：
计划文档路径：{路径}

重点检查：
- 模块职责是否越界（任务是否被分配给了错误的模块）
- 是否违反功能职责分离原则
- 是否违反关键架构决策中的约束（如通信方式、技术选型等）
- 是否引入了被禁止的反模式

输出格式：列出所有违规点，每个注明违反了哪条原则及修改建议。无违规则明确说明"未发现问题"。
```

### 3+ 号：代码可行性评估

```
你是代码可行性评估员。

第一步：阅读以下架构源文件，理解本模块的架构定位和约束：
{架构文件路径列表}

第二步：探索 {模块路径} 的代码现状。

第三步：评估以下计划任务在当前代码上的可行性：
{相关任务列表}

检查要点：
1. 当前代码结构是否支持这些修改
2. 是否有计划未提及但必须同步修改的内容（可能带来实施风险）
3. 实施是否可能破坏架构要求（以架构文件为准，不是以当前代码为准）

重要：如果当前代码本身不符合架构要求，那不是"现状可以接受"的理由——仍然以架构要求为准判断计划是否合理。

输出格式：每个任务给出可行性结论（可行/需调整/有风险），附说明。
```

## 注意事项

- 子智能体之间互不共享上下文，各自独立阅读架构源文件和计划文档
- 架构优先级高于一切：计划与架构冲突时，修改计划而非忽略架构
- "当前代码现状"≠"架构要求"：代码可能已经偏离架构，不能把偏离当作既定事实
- 此技能的输出是修改后的计划文档，不是单独的审查报告
